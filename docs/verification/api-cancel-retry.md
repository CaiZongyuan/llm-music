## Scope and observable behavior

Public application HTTP cancels a Project's queued/running Job, reads domain errors, lists retained Jobs, and explicitly retries failed/cancelled work with a new application/attempt identity. Migration `0004_job_cancellation` retains cancellation intent without adding a sixth public state. A dispatch acknowledgement is not terminal cancellation; saving/completed results cannot be downgraded. A retry retains original inputs and leaves the original Job/error/provenance untouched, but verifies current readiness and records current registry facts with `retry_of_job_id`.

Before calling Runtime submit, a fresh transaction writes durable `submitting`. Any unexpected post-dispatch exception or unconfirmed acknowledgement remains uncertain; a failed Job with no acknowledgement does not prove non-execution. Retry of uncertain work uses read-only recovery/current status and requires a verified original graph and independently confirmed safe terminal outcome. Unknown active work is never automatically resubmitted. Full restart reconciliation/exact graph restoration is #25 scope; conservative refusal remains valid until that evidence exists.

The shipped Comfy adapter reuses P0 pending deletion and the pinned target-aware `/api/jobs/{id}/cancel` mutex guard. It verifies original attempt/client/graph, rejects ambiguous ownership, and sends no global interrupt or whole-queue mutation. Pending removal checks readable queue absence/history; a running target requires its owned interrupted history and normalized cancelled status. Target switching preserves actual success or an explicit non-dispatched outcome. The application-pending cancellation/dispatch boundary and terminal mutations share one lock; the worker/importer preserve terminal state.

Native OOM/model/operation failures become domain messages/actions; private native exception details and application/native correlation remain in structured logs. A cancellation connection failure is Runtime uncertainty rather than an Asset-storage error. Completed import clears transient cancellation diagnostics in its own transaction. Existing Reference Audio, Candidates and saved Version snapshots/files remain owned and readable.

## Shared impact, simplification and limits

Real consumers are the Runtime Protocol/Fake/Comfy adapters, Job schemas/routes, generation registrar, result importer, current migration/retained Jobs, diagnostics readers, OpenAPI/CLI and the optional #24 observation consumer. Runtime cancellation has no second adapter. Postcommit `on_change(JobRead)` and optional subscription factory expose public state/observations; a callback only queues evidence, the worker alone updates state/imports, and finally closes the source. Saving is durable before result validation/import. Observer failures cannot change a Job outcome.

The initial phase-rank heuristic was removed after non-author correction: the specification protects terminal/saving state, not a fixed global ordering of music phases. Current phase whitelist/subscription FIFO retains supplied observations; polling without phase evidence preserves the latest reliable phase, and source loss clears it. Terminal hints cannot complete or duplicate imports. #24 owns WS/broker/decoder/source-context validation and integration; none of those modules or dependencies is included in #23.

The bounded simplification pass reviewed the complete owned delta and immediate consumers. It unifies confirmed-cancellation field assignment without moving commit ownership, removes duplicate native ownership checks after an equivalent single proof, and normalizes progress at the existing boundary. It retains explicit uncertainty, independent validation, immutable inputs, terminal guards, source cleanup and failure evidence. No generic scheduler/graph/event framework was added. Paired guides include one maintained executable source.

Actual GPU smoke, completed-process reopen against real artifacts, final independent Standards/Spec reviews and hosted integration remain Root-owned. No performance, listening-quality, broad filesystem-race, multi-process scheduling or complete P1 acceptance is claimed here.
