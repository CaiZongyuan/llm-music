## Repairs, simplification and retained limits

The first phase-loss test set a plain running/null observation, which legally preserves the previous reliable phase in the backend. The CPU fixture now sends the existing `native_event_source_lost` observation, which clears phase; the same browser assertion passes. The first fixture also attached log handlers before Uvicorn configured logging, so its genuine shutdown was not acknowledged in the file. Handler registration now follows configuration, retaining observed shutdown messages. These were fixture repairs, not backend changes.

The first lost-retry test changed the original fixture outcome back to running before retry. The real API correctly rejected its unsafe original with409/retry_unconfirmed. The repaired fixture retains a confirmed safe terminal outcome; the lost202 acknowledgement then recovers the one accepted attempt. Failed runs remain in the owned logs/traces rather than being reported as passing evidence.

The bounded pass inspected the complete owned Job delta and immediate #34/#35/first-consumer interfaces against the fixed baseline. Socket handles and listeners stay in one per-QueryClient registry; all server snapshots stay in Query. Event hints coalesce for250ms, active HTTP polls remain the fallback, and old connection callbacks cannot touch a replacement connection. Source loss accepts a fresh null phase; there is no phase rank. Found retry records remove obsolete uncertainty copy. No generic event store, browser persistence of server state, extra runtime client or automatic retry framework was introduced.

WS snapshots are validated hints and trigger fresh HTTP reads instead of directly replacing Query state. This costs an additional GET for live confirmation and deliberately protects HTTP authority from untrusted terminal/future hints. Connection sequences are local, never durable replay cursors. Cancellation uses the original application identity; a submitted intent never fabricates cancelled. A new attempt is an explicit POST with a new Job identity. Network-uncertain retry creation stays blocked for that mounted intent until an existing attempt is found; known prerequisite rejection can be explicitly retried after restoration.

Result links use public Router navigation and remain source-compatible with sibling feature routes. Actual Score/Candidate rendering and continuous Player clock checks belong to #34/#35 integrated consumer verification, not this isolated branch's absent sibling routes. Shared navigation and chapter/CI registration are Root-owned. The monitor never connects to ComfyUI or exposes prompt/node ids. Existing P1 [cancellation](api-cancel-retry.md), [events](api-job-events.md) and [restart recovery](job-recovery.md) evidence remains valid for the unchanged backend. No whole API suite, repeated native cancellation or GPU inference was performed here.

## Bounded result-cache repair

Before final independent review, #35 identified that a page-local completed effect cannot refresh recently cached empty Project results after the creator leaves that page. Against frozen `d8e4f87c624d50ad021028cfd68341ef92a881d3`, two actual browser counterexamples reproduced exactly that symptom: an independent consumer read empty Assets/Scores/Candidates, unmounted those lists, observed a real completed Job through either `JobState` or list-only `projectJobsOptions`, and returned before the application's15-second freshness window elapsed. Persisted HTTP had2 Assets/1 Score/1 Candidate, while the returned UI still displayed Asset count0. Retained red logs/traces: `.scratch/p2-development/33-jobs/result-cache-red.log` and `result-cache-red-traces/`.

The repair changes only `features/jobs/queries.ts` production behavior. A first authoritative completed detail read, list read or operation response cancels older reads and invalidates the three exact Project result list keys. It does not import pending sibling modules, change Query signatures, invalidate Versions, resubmit work or repoll Jobs. Actual Assets keys and #34/#35 Score/Candidate keys were traced; the independent consumer uses the generated client and application Query client without a completion effect, cache invalidation call or internal Monitor method. Both counterexamples then passed in11.3s total and showed all four persisted result identities within the original cache freshness window. After the bounded pass, the complete affected controlled suite passed **12/12 in28.0s**, and the original public Job submission/stale-list consumer passed **1/1 in5.1s**. Web and browser strict types plus the production check build passed. These repaired-source receipts remain separate from the earlier10/6-case runs.

The earlier freeze, native/CPU limitations, accepted preview and all unrelated evidence remain bound to their original revisions. Root's combined #33/#34/#35 integration supplies the actual sibling pages, navigation, chapter registration and hosted CI.
